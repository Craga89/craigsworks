signs it would help

Is this you?

If a few of these ring true, it's probably worth a conversation.

  • Changes wait for a weekly or fortnightly release
  • A deploy needs a particular person around
  • CI takes long enough that people switch tasks while they wait
  • Flaky tests get re-run until they go green
  • Nobody can try a change until it's merged
  • Rolling back means a scramble and a late night

working together

What we would do together

In this order, because each step makes the next one easier, and you can stop after any of them.

  1. Measure

    Time every stage of the pipeline and find where the waiting really is. No changes yet, just facts.

  2. Speed up

    Fix the slowest steps first: caching, running in parallel, and building only what a change touches.

  3. Preview

    Give every change a place to be seen before it merges, for review, product and QA.

  4. Automate and hand over

    Deploys that check their own health and roll back, with runbooks and a walkthrough for the team.

what i've done before

From release days to every merge

I built Hive's CI/CD from scratch in 2019 and kept evolving it as the team and codebase grew. It's the clearest example of the kind of change I can help with.

then · 2019

Hosted pipelines, 18 repositories, a release train

  • Each repository built and deployed its own way
  • Work queued up for a scheduled release
  • A growing Cypress suite that slowed CI down

now

One monorepo, a graph-aware release engine, continuous deployment

  • Self-hosted Buildkite, defined in Terraform
  • A TypeScript build engine that builds and deploys only what a change affects
  • /deploy on a pull request puts it in a test environment
  • Deploys wait for healthy tasks and detect rollbacks, so a bad release stops itself
  • End-to-end tests moved to Playwright: faster and far more stable

how it evolved

  2. Buildkite + build engine
  3. continuous deployment
  4. merge queue · staging
  5. one Validate gate
