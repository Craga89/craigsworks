featured · ci/cd and release engineering · 2019 → today

Build only what changed, ship every merge

I built Hive's CI/CD platform from scratch and kept evolving it as the team and codebase grew. Today it runs on self-hosted Buildkite defined in Terraform, driven by an in-house TypeScript build-and-deploy engine that models the monorepo's dependency graph, so each change builds and deploys only the packages it affects.

  1. merge
  2. package graph
  3. build affected, in parallel
  4. Validate gate
  5. staging
  6. production

in practice

  • Merged work reaches customers automatically. No release train since 2022.
  • A small fix rebuilds a handful of packages, not the whole platform.
  • Every pull request passes one required gate, and /deploy puts it in a test environment.
  • Deploys wait for healthy tasks and detect rollbacks, so a bad release stops itself.
Full case study, on craigthompson.dev ↗

what it could mean for you

Not necessarily this exact set-up: a team of five doesn't need a custom build engine. But the same moves, in the same order, work at any size: measure, build less, preview every change, make deploys look after themselves.
